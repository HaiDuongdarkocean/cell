### D2 — CLOSED (`943ba57e`) — Manual `learning → tracking` demotion via vocabulary bulk-mark

Originally: `VocabularyTab` bulk "Change status → Tracking" wrote `tracking` onto `learning` rows through `setWordStatuses`, breaking "learning = card exists" until the next reconcile pass.

Fix verified: `demotesLearningRow` (`wordStatusStore.ts:76-87`) rejects `unknown`/`tracking` writes onto a stored `learning` row inside the store itself — `setWordStatus` (`:202`), `setWordStatuses` per-term filter (`:310`), `setWordStatusPos` (`:631`, reading the pos row with term-row fallback). Every user write seam funnels through these: keys, popup, vocabulary cycle/bulk, `SrsDeckDetail.markStatus`, and the `WORD_STATUS_SET`/`WORD_STATUS_SET_MANY`/`WORD_STATUS_CYCLE` handlers — no path bypasses the store. Sync writers (`setWordStatusFromSync`, `setWordStatusesFromSync`, `clearLearningFlag`) are untouched, so card-loss clears and `tracking→learning` escalation still work. New tests assert: `tracking`/`unknown` demotions no-op on `learning`, `known`/`ignore` still land, bulk filtering keeps per-term semantics, pos writes can't demote a term-level `learning` row (`wordStatusStore.test.ts` learning-guard block).

## Risks accepted / observations

- **R1 — `demotesLearningRow` also blocks user `unknown` writes on `learning` (stricter than D2 required):** the fix treats `unknown` as a forbidden demotion alongside `tracking`. This conflicts with REQ-3's literal rule "setting `known`/`ignore`/`unknown` clears the stored flag" and REQ-4's "explicit user base-write wins" wording — but is consistent with the spec's own state machine (no user edge `learning→unknown`), with `learning` being system-managed, and with the fix's stated intent ("the only user edges out of learning are the terminal bases `known`/`ignore`"). Practical effect: key `1` / an `ignore→unknown` cycle on a `learning` word silently no-ops; a *stale* `learning` flag (card already gone) cannot be user-cleared via `unknown` — it still heals via the next `reconcileLearningFlags` pass (Anki sync, SRS page open, or deck delete) or via `known`/`ignore`. Accepted as the stricter, spec-machine-consistent reading; the spec wording could use a clarifying note but no code change is needed.

- **Latent arbitration hole:** a *non-user* `tracking` candidate with a fresher `sourceAt` can demote a stored `learning` (`wordStatusArbitration.ts:60-67`; the test suite documents this as intentional: `learning→tracking is a downgrade — normal arbitration applies`). No current system writer emits `tracking`, so unreachable today — worth guarding if an import/sync path ever emits `tracking`.
- **Sync-written flag changes emit no `WORD_STATUS_CHANGED`** — token surfaces repaint only on the next status resolution (lookup, cue re-render, `SYNC_DATA_APPLIED` relay, or local emit). Matches the pre-existing Anki-sync pattern and REQ-4's accepted staleness; the new SRS card-loss path inherits the same lag.
- **`restoreWordStatus`/`trashWordStatus` bypass the demotion guard** — trash deletes the row outright (user delete = explicit removal), restore writes `previousStatus` verbatim (`wordTrashStore.ts:145-147`). Neither can *fabricate* a flag — restore only replays a previously-legitimate value — and unknown-family drift self-heals on the next card event or reconcile. Consistent with "user delete/restore wins" semantics.
- **Cue list does not apply i+1 gating** — `CueList.tsx` renders capsules/freq bands on every not-known token regardless of `iPlus1`. Pre-existing scope decision from the i+1-gate commit (`b4019daa`), unchanged here.
- **Legacy `useDictionaryLookup.cycleStatus` write path** still exists outside the REQ-1 write-path inventory; it is safe (`nextStatus` returns base-only) and consumed only by removed/design mockups.
- **Showcase/dev mock handlers** (`design-system-showcase/mockDictionary.ts:416`, `VocabularyPanelPage.showcase.tsx:152`) accept/seed any status incl. `learning` via the sync writer — dev-only surfaces, correct usage.
