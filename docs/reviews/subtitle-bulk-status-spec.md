# Spec Review — subtitle-bulk-status

<findings>

Blockers:
1. [REQ-2 step 3 / NFR-2 / REQ-1] [TL]: the spec claims the local-player cue list is light DOM ("document root for light DOM, registered shadow roots on streaming") — it is NOT. The shared `useSplitView` path attaches an open shadow root for the panel in BOTH contexts: `subtitleSplitView.ts:280` (`panel.attachShadow({mode:'open'})` → `panelInner` → `setSplitViewPortalTarget`), `SubtitlePanels.tsx:401-425` portals `SubtitlePanel`/CueList into it, and the local player opts in via `fallbackPlayerContainerRef={stageRef}` (`PlayerView.tsx:395`). Built literally per spec, the local-player controller's `getShadowRoots()` returns `[]` (`subtitleTokenizeController.ts:178-186`) → `allowedRoots={document}` (`selectionTerms.ts:87-94`) → panel selections are filtered/retargeted away → key falls to `hoveredTerm` (never set by CueList) → returns false → AC-1 fails. Fix: spec must require the local-player controller to wire `getExtraShadowRoots` → `[data-cell-split-view="panel"].shadowRoot` (same pattern as `contentScriptController.ts:342-345`), and correct REQ-2 step 3 + NFR-2 to "document root for overlay/page text + panel shadow root in both contexts".

Major:
1. [REQ-1 / REQ-2 / §Flows] [BA/TL]: the headline change — instantiating the status-key path in the local player — is specified only implicitly ("reuse createSubtitleTokenizeController", parenthetical in §Flows). REQ-1 omits the required wirings: `onOpenDictionary` (non-optional param, `subtitleTokenizeController.ts:41` → `webTextCtrl.handleLookup`), `getPopupStatusTarget` (needed for AC-5 "popup term wins… local player included" → `webTextCtrl.getPopupStatusTarget`, `webTextDictionaryController.ts:271`), mount/lifecycle (created/destroyed when), and the new `getExtraShadowRoots` (see Blocker). Fix: add an explicit wiring list + lifecycle to REQ-1 or a new REQ.
2. [REQ-3 / REQ-4 / REQ-6 / §Data / §Flows] [PO/TL]: selection-store topology undefined — "the shared tokenize selection store" (REQ-3) vs "per tokenize session" (§Data/REQ-6). In code each controller creates a PRIVATE `TokenizeStateStore` (`subtitleTokenizeController.ts:69`, `webTokenizeController.ts:131`), each `statusKeyControls` reads exactly one store, and `SubtitleTokenizeController`'s public API does not expose it. Unstated: which store backs cue-list ctrl+click per context; cross-store apply semantics on streaming (ctrl+click page text → web store, ctrl+click cue list → subtitle store → one keypress applies only the first listener's store, the other keeps stale marks); REQ-4's "every rendered token whose term ∈ selectedTerms" marking scope. Fix: name the selection-store owner per context (cue-list selection must live in the same store the context's `statusKeyControls` reads — requires exposing a selection API on the controller), state cross-store semantics, and scope REQ-4 marking accordingly.
3. [REQ-4 / AC-8 / N8] [BA]: the a11y half of N8 evaporates — REQ-4 defines only the `js-cell-token--selected` CSS class; NFR-5's "controls expose accessible names" does not cover token spans; no AC verifies AT exposure (intent N8 + draft AC require "selected state readable by AT"). Fix: REQ-4 Rules must name the accessible-state mechanism (e.g., `aria-selected` on token spans or a defined equivalent); AC-8 must include an AT-verifiable line.
4. [REQ-5 / Success Criteria] [BA/PO]: no AC verifies cross-surface convergence — REQ-2 step 5/REQ-5 postcondition claim panel+overlay+popup+other-tabs repaint, but AC-1 checks only panel recolor and AC-5 checks popup priority, not popup/second-surface repaint. Fix: add an AC — after a bulk apply on one surface, every other live surface showing a changed term (incl. an open dictionary popup) repaints via `WORD_STATUS_CHANGED`.
5. [REQ-2 Rules / REQ-3 / AC-2 / §Flows] [BA/PO]: two parity ambiguities. (a) `hoveredTerm` fallback is a dead path on cue-list surfaces — CueList wires no hover (`CueList.tsx:113`), so "works identically on … panel" is false for the hover→1-4 gesture unless the contract gains a hover member or the claim is scoped to bound-span surfaces. (b) Intent TO-BE 2 says "the same gestures" work on the local-player overlay, but REQ-3/AC-3 limit ctrl+click to cue-list tokens — the controller reuse wires `onTokenCtrlClick→toggleSelectedTerm` for free (`subtitleTokenizeController.ts:95`), so state explicitly that overlay bound spans support ctrl+click in the local player too. Fix: scope both claims explicitly.
6. [REQ-1 step 3 / Objective line 7 / REQ-3 alt] [TL]: factual misstatements. (a) "binds token spans for the active cue ± window" is wrong — `render()` binds only `activeTargetIndex` (`subtitleTokenizeController.ts:230-256`); ±`DEFAULT_WINDOW` is the preloader's prepare scope. (b) "ctrl+click does not [work] in the panel" is imprecise — today ctrl+click on a cue-list token opens the dictionary (`CueList.tsx:113` fires `onTokenClick` regardless of modifier); the spec intentionally diverts a live gesture and must say so, incl. that CueList must intercept ctrl/meta before `onTokenClick` like `tokenSpanRenderer.ts:68-71`. Fix: correct both statements.
