## Scope

- **In:**
  - Bind every sub-floor interactive element in the Universal Panel surface to `--touch-target` via min-height + invisible hit-area growth: `Toggle` (all sizes used in panel), dict-link rename buttons, "Show hint" buttons, xs/sm circle `IconButton`/`Button` uses (mode-card kebab, vocab trash/edit-delete, dictionary toolbar), profile flag, `.statusBadge`, MobileSheet `.handle`, BottomSheet close, dict-popup tabs, audio-tester play, and inputs/selects sized off `--size-element-md` (min-height binding; visual height policy decided in SPECIFY/DESIGN).
  - Focus-trap fix: initial focus pick skips `display:none` elements (reuse the `:41` visibility filter) and BottomNav moves after `.body` in the DOM (or equivalent) so mobile focus order matches visual order; verify every tab opens with focus inside the dialog.
  - Semantic batch: tablist pattern OR documented nav-rail semantics for the tab strip (decision recorded in the doc/design); `radiogroup` for custom mode cards; `aria-expanded`/`aria-controls` on the Advanced disclosure or Accordion swap; single `role="status"` replacing per-card `aria-live`.
  - Coarse-pointer verification: re-run the audit spec (or a scoped derivative) under emulated coarse pointer (`isMobile`+`hasTouch` descriptor or CDP media override — `hasTouch` alone doesn't flip `pointer: coarse`); produce a zero-violation evidence list.
- **Out:**
  - Visual restyle of the controls — glyphs/pills keep their current look; only the hit area grows (N2).
  - Mobile-nav structure, item count, label legibility, tokenize capsule sizing, sheet grabber/peek affordance, page-bleed, 600–839px chrome → item 31 `up-mobile-chrome` (declares this item as a dependency — this item supplies the hit-area + focus floor it builds on; it must not undo these bindings).
  - Settings sub-nav 13-icon strip → item 32 `up-settings-subnav`.
  - Tab scroll/padding/mounting contract (F-1/F-5/F-19) → item 28; token-name typos, native-atom migration, Escape/role craft (F-6/F-21/F-22/F-24) → item 29; selected-state recipes and status-chip visual consolidation (F-13/V-3) → item 33.
- **Non-goals:** not a whole-extension accessibility audit — scope is the Universal Panel surface (its shared atoms only insofar as their size bindings reach the panel); not touch-gesture engineering (BottomSheet drag is item 31); not a WCAG certification exercise — the floor is the project's own STANDARD §10.3 contract.

## Workflow

A maintainer picks the item with the audit's measured violation list as the work queue. Each pass through the queue is the same motion: find why a control misses the floor (a fixed size token, a `min-height: 0` carve-out, a size variant that never reaches `--touch-target`), bind it to the token — preferring `min-height`/`min-width` or transparent padding over layout height so dense rows don't reflow — and move on. The shell fix is separate and small: `useFocusTrap` applies its existing visibility filter to the initial pick, and the BottomNav node moves after the body so DOM order equals visual order on mobile. The semantics pass swaps ARIA roles/attributes without touching visuals: the tab-strip decision (tablist vs documented nav rail) is made once and written down, customs cards join a `radiogroup`, the Advanced toggle gains disclosure semantics, and the playlist's per-card live regions collapse into one status announcer. The stage ends with a verification loop: the existing audit spec re-runs under emulated coarse pointer; any control still under 44px goes back through the queue until the violation list is empty — that's the milestone. The work finishes when keyboard, touch, and screen-reader journeys all pass on the same build.

## Journey

### AS-IS

1. An older learner with a mild hand tremor opens the panel on a tablet and tries to flip "Sync word status" in Settings — the switch is a 20px input in a full-width row; they miss twice, hit dead padding, and give up (nine settings toggles all measure 20px).
2. The same user tries to rename a dictionary link — the rename button measures 18.7px, below even the WCAG 24px minimum — and the vocabulary status badge they want to cycle is a 20px pill on an otherwise roomy row.
3. A keyboard-only user opens the panel on the Vocabulary tab; `aria-modal="true"` promises containment, but the trap's first focusable is the `display:none` bottom-nav button, so `.focus()` no-ops and focus stays on the background page — the first Tab can walk out of a "modal".
4. On a phone, the same user presses Tab and lands on the visually-last bottom nav first — DOM order and visual order disagree, inverting the announced sequence.
5. A screen-reader user hears a flat pile of buttons where six tabs should be; expanding "Advanced" announces only "switch, on" with no hint a section appeared; the custom mode cards announce as radios with no group; and every playlist status churn re-announces entire card contents including button names.

### TO-BE

1. The tremor user taps the same toggle — an invisible hit area now spans ≥44px around the unchanged visual switch — and it flips on the first try; rename, hint, badge, kebab, profile flag, sheet handle, close, and every input meet the same floor.
2. Dense rows look identical — the status pill is still a 20px pill visually, but its target is the full 40/44px — and no grown hit box swallows a neighbor's tap.
3. The keyboard user opens any tab and focus lands on a visible control inside the dialog; Tab and Shift+Tab cycle within it and restore on close; on mobile the bottom nav is the last stop, matching what sighted users see.
4. The screen-reader user hears either "tab list, six tabs, Vocabulary selected" with arrow-key navigation or a clearly-labelled navigation landmark with `aria-current`; custom mode cards announce "radio, 2 of 4, Custom modes"; the Advanced toggle announces "expanded" and names the region it controls.
5. When a playlist recording finishes processing, a single status announcer reports the summary once — cards themselves stay silent.
6. Re-running the audit under emulated coarse pointer reports zero interactive targets under 44px — the accessibility floor is measured and proven, not assumed.

## Stories

- S1: As a touch or low-dexterity user, I want every control in the panel to present a target of at least the pointer's floor size, so that I can operate it on the first try — done when a coarse-pointer measurement finds no interactive element below 44px and a fine-pointer pass finds none below 40px.
- S2: As a user of dense tool rows, I want the enlarged targets to leave the visual design untouched, so that the panel doesn't grow taller or more crowded — done when sub-floor controls keep their visual size while their hit boxes meet the floor without overlapping neighbors.
- S3: As a keyboard user, I want opening the panel to put my focus inside it on a control I can see, so that the modal's containment promise is real — done when opening on every tab lands focus on a visible element and Tab/Shift+Tab never escapes.
- S4: As a keyboard user on mobile, I want the tab order to match the visual order, so that I reach content before the bottom navigation — done when the bottom nav is the last focusable stop, matching its visual position.
- S5: As a screen-reader user, I want the six destinations announced as a coherent set, so that I know where I am and how to move — done when the strip exposes tablist semantics or a documented nav-rail contract with current-state and labelled panels, and the choice is recorded.
- S6: As a screen-reader user picking a study mode, I want custom mode cards announced with their group and position, so that presets and customs aren't a confusing pile — done when custom cards sit in a radiogroup.
- S7: As a screen-reader user, I want the Advanced control to tell me a section appeared, so that I'm not hunting for content that silently rendered — done when the control exposes expanded state and the region it controls.
- S8: As a screen-reader user monitoring playlist processing, I want status changes announced once, so that I'm not drowned in re-announcements — done when a single status region carries the summary and no card carries `aria-live`.

## Decision

go — every claim is measured evidence (computed styles, line-cited code), the fix is binding existing components to an existing token plus small ARIA/DOM edits, the verification harness already exists, and the panel's P0-class failures (focus outside an aria-modal dialog, sub-24px targets) are the cheapest real accessibility wins in the backlog. Downstream item 31 depends on this floor.

## Draft Acceptance Criteria

- [ ] Under emulated coarse pointer — `isMobile`+`hasTouch` device descriptor (e.g. `devices['Pixel 5']`) or CDP `Emulation.setEmulatedMedia` with `pointer: coarse`; `hasTouch: true` alone does not make `@media (pointer: coarse)` match in Chromium — no interactive element inside the Universal Panel measures below 44px; under fine pointer, none below 40px — measured via the audit spec's `touchTargetViolations` list returning empty.
- [ ] The sub-24px failures are eliminated: settings/study-mode toggles, dict-link rename buttons, and the vocabulary status badge each present ≥ the floor while their visuals may stay compact; no grown hit box overlaps a neighboring control's target.
- [ ] Opening the panel on any of the six tabs moves focus to a visible element inside the dialog; Tab and Shift+Tab cycle within it without escaping; closing restores focus to the trigger.
- [ ] On mobile layout, the bottom navigation is the last focusable element in the panel, matching its visual position; tab order follows visual order.
- [ ] The tab strip exposes either `tablist`/`tab`/`tabpanel` semantics with arrow-key navigation, or documented nav-rail semantics with `aria-current` and accessible names on the panes — the decision recorded in the spec/design docs.
- [ ] Custom study-mode cards are grouped under `role="radiogroup"`; AT announces group membership and position for presets and customs alike.
- [ ] The Advanced disclosure announces expanded/collapsed state and identifies the region it controls (`aria-expanded` + `aria-controls`, or the shared Accordion/Collapsible).
- [ ] Playlist status changes announce through a single `role="status"` region; no card carries `aria-live`; the summary conveys which/how many recordings changed state.
- [ ] The verification pass runs as part of the deliverable evidence: coarse-pointer violation list empty, plus keyboard focus-order and SR-semantics checks recorded.
