# Audit Technical Debt

> **Debt is invisible until you name it, score it, and rank it.**

This skill turns a vague "the code is messy" feeling into a verifiable inventory, a weighted score, and a ranked plan.

## When to Use

- The user asks to audit, assess, or prioritize technical debt.
- A roadmap or refactor is being planned and needs a debt map.
- A specific module is considered risky and needs a structured review.
- Post-mortem, incident, or velocity drop points to hidden debt.

## When NOT to Use

- The task is to fix one bug or add one feature.
- The user wants a quick "is this function clean?" review.
- The request is about team process or project management without code.

## Core Principle

> **Audit = signal + classification + scoring + communication.**

If any of those four is missing, the result is either a tooling report nobody reads or a gut feeling nobody trusts.

## The Workflow

### Step 1 — Scope the audit

**Purpose:** Avoid paralysis by cataloging the whole codebase at once.

**Actions:**
- Ask the user which system, module, or file group to audit.
- If they say "all of it", pick the top 3 areas by recent change, risk, or business value.
- Write the scope as one line: "Audit X to find debt blocking Y."

**Guard:** The scope names a concrete boundary (file path, feature, or module).

**Loop back:** If the boundary is "everything", ask for one risk, one recent incident, or one upcoming feature.

---

### Step 2 — Collect automatic signals

**Purpose:** Find debt the code already admits and the metrics already measure.

**Actions:**
- Run `grep` for `TODO`, `FIXME`, `HACK`, `XXX` and `technical debt` in the target scope.
- Check unit / integration test coverage for the scoped area; flag flaky or timing-sensitive tests that fail under load.
- Run lint, typecheck, and build; record failures and warnings.
- Check dependency freshness (`npm outdated`, `cargo outdated`, etc.).
- Record file churn (git log --stat or git diff) if available.
- List the largest files by line count and flag files over a project-specific threshold (e.g., >500 lines).
- Note high cyclomatic-complexity hot spots.

**Guard:** You have at least one automatic signal for the scoped area.

**Loop back:** If no signal, the scope is too narrow or the tooling is missing. Widen the scope or state the tooling gap.

---

### Step 3 — Collect human signal

**Purpose:** Capture architectural and business-logic debt that tools miss.

**Actions:**
- Ask the team: "What code do you avoid touching? Why?"
- Ask: "What recent feature took 2x longer because of existing code?"
- Ask: "Which dependency or module scares you to upgrade?"
- Merge the answers with the automatic signal list.

**Guard:** You have at least one human observation about the scoped area.

**Loop back:** If no human is available, infer from commit messages, PR descriptions, and code comments. Flag the inference as lower confidence.

---

### Step 4 — Classify each item

**Purpose:** Put every debt item into the right bucket so the fix uses the right approach.

**Actions:**
For each item, pick one primary type:
- **Code quality** — duplication, complex functions, poor naming, inconsistent patterns.
- **Architectural** — wrong boundaries, tight coupling, data-model mismatch.
- **Infrastructure / dependency** — outdated libs, stale toolchain, manual config.
- **Testing** — missing tests, flaky tests, slow tests, low coverage.
- **Documentation** — missing or stale docs, onboarding by tribal knowledge.
- **Process** — unclear ownership, manual steps, missing gates.

**Guard:** Every item has a primary type and a one-sentence description of the problem.

**Loop back:** If an item fits two types, pick the one with the highest reach or risk.

---

### Step 5 — Score each item

**Purpose:** Compare debt across categories with a common currency.

**Actions:**
Score each item 1–5 in four criteria. Use the weights to compute a weighted score.

| Criterion | Weight | 5 means | 1 means |
|---|---|---|---|
| **Velocity impact** | 30% | Nearly impossible to change without touching the debt | Minor friction |
| **Risk** | 35% | Active vulnerability, outage risk, or frequent bugs | Theoretical, no observed failure |
| **Reach** | 20% | Every team / feature / user touches this | Isolated subsystem |
| **Inverse remediation cost** | 15% | Can fix in < 1 sprint | Multi-quarter rewrite |

`weighted score = 0.30×velocity + 0.35×risk + 0.20×reach + 0.15×(6 − cost)`

**Example row:** a module with velocity=4, risk=4, reach=5, cost=2 scores `0.30×4 + 0.35×4 + 0.20×5 + 0.15×4 = 4.20`.

**Guard:** Every scored item has the four numbers and the final score.

**Loop back:** If an item cannot be scored, flag it as `unscored` and schedule a spike.

---

### Step 6 — Build a ranked inventory

**Purpose:** Turn scores into a visible backlog.

**Actions:**
- Create a list sorted by weighted score descending.
- Group by primary type.
- Add columns: location, type, description, impact, score, remediation size, owner if known.

**Guard:** The inventory has at least the top 5 items and a total item count.

**Loop back:** If the inventory has fewer than 3 items, the scope is too narrow.

---

### Step 7 — Translate to business language

**Purpose:** Make the audit useful to non-technical stakeholders.

**Actions:**
For the top 3 items, rewrite the impact:
- Replace "high cyclomatic complexity" with "adding feature X will take Y extra days."
- Replace "outdated dependency" with "upgrade to dependency A is currently B hours; in 6 months it will likely be C weeks."
- Replace "low test coverage" with "changing this area has a X% chance of production regression."

**Guard:** Each top item has a one-line business impact with a specific time, money, or delivery estimate (e.g., "adding feature X will take Y extra days" or "this will block Z release").

**Loop back:** If the business impact is still technical, ask "what would this cost the product owner?"

---

### Step 8 — Recommend a remediation roadmap

**Purpose:** Give the user something they can schedule.

**Actions:**
- **Quick wins:** top 3 items with low cost and medium-high score.
- **Pay-down plan:** top 3 high-score, high-cost items; schedule across sprints.
- **Watch list:** medium-score items that are stable and rarely touched.
- **Stop-loss:** any reckless/deliberate debt taken to meet a deadline; mark it for payback before the next major change.

**Guard:** The roadmap has at least three concrete actions; at least one has an owner and every item has a cadence.

**Loop back:** If no quick win exists, suggest a spike to reduce uncertainty before committing.

## Output Template

```markdown
## Technical Debt Audit — <scope>

### Summary
- Items found: N
- High score (≥4.0): K
- Quick wins: Q
- Big bets: B

### Inventory (top 5)
| Location | Type | Description | Velocity | Risk | Reach | Cost | Score |
|---|---|---|---|---|---|---|---|
| ... | ... | ... | ... | ... | ... | ... | ... |

### Business impact (top 3)
1. ...
2. ...
3. ...

### Recommended roadmap
1. Quick win: ...
2. Pay-down: ...
3. Watch: ...
```

## Anti-Patterns

| Don't | Why |
|---|---|
| Treat all TODO comments as debt | Some are reminders, not risk. Classify first. |
| Score only code quality | Architectural and dependency debt often hurt more. |
| Skip the business translation | Debt only gets fixed when product sees the cost. |
| Recommend a full rewrite | Pay down gradually near areas of high change. |
| Ignore the team's fear | Tools miss the debt engineers are avoiding. |

## Common Rationalizations

| User says | Respond |
|---|---|
| "Just clean up the code" | Clean up what, where, and how does it help velocity? |
| "This module is a mess" | Which category? Code, architecture, or dependency? |
| "Fix all the TODOs" | Which TODOs affect the next 3 features? |
| "We don't have time for debt" | Which debt is already slowing this sprint? |

## Verification

- [ ] Scope is concrete.
- [ ] Automatic and human signals were both collected.
- [ ] Every item is classified into one of the six types.
- [ ] Every item has a weighted score.
- [ ] Top items have a business-language impact.
- [ ] Roadmap has at least one quick win and one pay-down item.
- [ ] Output uses the template or explains why not.
